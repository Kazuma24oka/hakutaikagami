# 部隊宛の既知不達後再送

## この工程の完成条件
1. 初回の命令原本・発送・不達・返書を変更せず、省略可能なUnitRetry台帳へ追加便を保存する。旧保存はこの項目を持たずに読める。
2. 同じ原本の直近便について本人が失敗報告を実受領した場合のみ再送できる。原本ID/本文/初回時刻は維持し、配送試行は最大3便。既に正式受領済みなら再送しない。
3. 宛先を最後に観測した本隊所在地または宣言済みの帰還拠点から明示選択する。未観測の現位置へ補正しない。各便は別の匿名伝令役と実地形経路を持つ。
4. 受令・適用・返書の受領を分離し、再送時刻で原命令の権限/優先順位を更新しない。新しい現地命令は旧原本より優先し、同じ原本の効果は最大1回。人物・兵・所有者・兵糧は増やさない。
5. 原本・試行・効果・匿名伝令・往路/復路を別IDで検査し、途中保存から同じ未来・3D数値・画素を比較する。改ざん保存を拒否し、旧入口も回帰する。

この範囲で照会・遅着回収・失敗返書そのものの回復まで完了したとは扱わない。それらは次の小工程として続ける。3便制限は既存共通MessageFlowの規則で、別の配送時計を作らない。

## 既存原本の扱い
原本中のAddressEvidenceは初回発送時の観測根拠として不変。配送し直す新しい経路/宛先/根拠はUnitRetry.Dispatchesへ固定する。宛先変更は命令内容や受信権を変更しない。現地実受領でのみ命令を評価し、受信役は既存本隊の受信役のまま。伝令の匿名役は配送便ごとに分け、以前の伝令を瞬間移動させない。

## 次の五作業
1. 本工程の既知不達後再送を実装・復旧・3D・同ブランチpushまで完了する。
2. 実受領した照会への物理返書を追加し、引用情報と原本の正式受領を区別する。
3. 返書自身が届かなかった場合の既知宛先への回復を追加する。
4. 実在する保持便と受渡し経路を持つ遅着回収を追加し、原本/再送の競合と一度だけの適用を検証する。
5. 軍務再任・複数案件へ接続する前に、貸与元・所有・本人の知識が案件間で混ざらないことを検証する。

新しいゲーム上の根本仕様が必要になった場合のみ判断を求める。上記の技術実装・検証では工程ごとの確認待ちを挟まない。

## 終了時の素材所有

回帰で見つかった終了時の参照漏れも本工程で修正する。画面側のフォント/生成テクスチャを所有者が解放し、プロセス終了時だけ画面破棄→共有LOD/素材の参照解放→管理側回収→描画エンジン終了の順にする。通常のメニュー復帰やロードで共有素材を解放しない。起動/復旧/終了の反復と最終回帰でERRORがないこと、および終了処理の実行マーカーを確認する。元の失敗ログはruntime-local/correctionsへ保持する。C#の参照カウント資源は即時には解放されない場合がある（[Godot4.5公式RefCounted](https://docs.godotengine.org/en/4.5/classes/class_refcounted.html)）。
