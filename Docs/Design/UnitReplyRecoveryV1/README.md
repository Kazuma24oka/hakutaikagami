# 返書自身の物理不達回復

## 完成条件
1. 新しい撤退命令/部隊照会の原本だけに返書配送方針を明記する。既存入力/本文/保存は任意項目を省略し、旧返書へ自動再送を遡及適用しない。
2. 受令して書かれた返書が本人不在で届かない場合、同じ伝令が不達報告と原本を返書発送時の部隊所在地へ持ち帰る。部隊が不在なら失敗を知った扱いにしない。
3. 部隊側が直近不達報告を共通MessageFlowで実受領した後だけ、同じ返書原本/内容/報告時刻を最大3便まで再送する。新しい便は別の匿名伝令、宛先は元の既知本人所在で真の現位置へ補正しない。兵/資源/人物を増やさない。
4. 初回不達を不変に保ち、持ち帰った原本と未受領報告を実際の保持者/地点へ保存する。保持者と再送便を別々に表示し、同じ伝令が二重存在しない。原本の正式受領は一度だけ。
5. 通常入口の甲府/小田原/浪人開始と移動部隊への報告不達で、12保存点ずつから同じ未来/実描画座標/画像を比較する。改ざん/欠落保存を拒否し、影響範囲の代表旧機能・全単体テスト・動画を検査して同ブランチpush。

## 仕組み
`PostPolicy`/書状本文の`ReplyPolicy`を省略可能にし、新規通常画面の発信だけで版を固定する。`ReplyRecovery`に失敗報告/再送の経路・到達・原本保持を記録する。共通配送の原本/試行/正式受領/本人または受信役の知識を使い、別の配送時計を作らない。到着境界は既存共通MessageFlowのDueAtへ接続済み。

最初の`TroopReply.Received=false`は過去の観測として不変。後からの受領は追加試行と共通正式受領で表す。届いたかどうかの表示も共通知識を読む。原本を持ち帰った伝令はその地点で保持し、新しい便をそこから出す。報告自体も届かなければ、その紙も同じ伝令が保持する。匿名伝令は技術上の運搬役であり、架空武将や兵の追加ではない。文具/伝令費用の経済や健康は対象外。

同時に複数の伝令がいる場合も、それぞれの記録された位置から表示する。描画の補間は見た目だけで、共通時計/実移動速度を変えない。小さい広域モデルやラベル重なりは最終外観の受入れではない。

原命令が不達だった場合の最初の不達報告は、従来の物理便のまま。本工程の自動回復は受令後に部隊が書いた返書が対象。保持された未受領紙の実物遅着、原本/再送分の競合は次工程で続ける。保持は受領や内容認識ではない。

次の5件：1.本工程の全照合/同ブランチpush、2.保持紙の現地受渡し/物理遅着、3.遅着と再送の重複/一度だけの効力、4.再任/複数案件、5.観測/敵対と全国負荷。重要な未承認判断以外は継続する。
