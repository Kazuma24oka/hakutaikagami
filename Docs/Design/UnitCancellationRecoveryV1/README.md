# 取消結果の不達回収と終了した指揮権

完成条件は次の5件。
1. 取消の効力結果を運ぶ伝令が本人不在で失敗したら、本人は結果を知らず、実物の書状と保持者が実際の地点に残る。
2. 同じ本人が現地で書状を受け取った時にだけ結果を知る。回収によって取消・停止命令・過去の兵糧消費を繰り返さない。
3. 取消の期限ちょうどは受領し、期限後は原本・再送・実物遅着で延長しない。指揮返還後の未来効力で権限を復活させない。別原本が同秒到達しても古い対象の取消に巻き込まない。
4. 通常入口の実画面で不達から回収、本人と兵の合流、帰還、兵糧返納、返報、指揮返還まで動かす。各16保存点を別プロセスで復旧し、全世界と3Dの位置・実画像・同じ未来を比較する。
5. 全Coreテスト・既存の代表回帰・実画像/動画・資源解放・ソース照合後に同ブランチへcommit/pushする。未再実行の過去ケースを現行成功件数へ混ぜない。

既存取消モジュールと共通配送をそのまま使う。本人が移動して失敗した結果書状を、実保持者から同一試行の遅着として受領する。原本の不達や取消効力の履歴を成功に置換しない。通常の取消伝令表示は撤退原本と区別する。

未来効力の編集は公開Core入力で検証し、通常UIの予約編集は未実装。回収試作の全景は技術用表示で、最終の認識別可視範囲やラベル品質の採用ではない。19秒・固定60fpsの動画は実画面の動作確認で、実時間性能測定ではない。

次は同じ主君・実在する同じ守備隊への再任と案件別の履歴を接続する。兵糧や損耗を初期化せず、過去の書状を破棄せず、古い軍務の命令で新しい貸与を動かさない。同時に複数の主君から貸与を受ける機能や史実勢力との交戦は、この工程の完成として扱わない。

検証：verify_unit_cancellation_recovery.py → 実画像・復号動画 → --finalize → check_unit_cancellation_recovery_binding.py。過去工程の検証記録はその当時のソースの実績として保持する。
