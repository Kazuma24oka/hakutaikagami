# 撤退命令の正式受領期限

共通契約CC-12に従い、部隊受信役の正式受領時刻で命令の到達期限を判定する。期限Tちょうどは有効、Tを過ぎれば無効。本人へ戻る受令返書は別の配送で、この原命令の受領期限を流用しない。再送/保持原本でも同じ原文・期限のままである。

完成条件は5件。
1. 新規DeliverByを原命令の発送時に固定し、部隊が実在しても期限後なら受領/実行しない。
2. 初回のDelivered/Lost/Rejectedを保存し、遅着後も初回台帳を変更しない。旧期限なし保存は新項目を省略できる。
3. 既知の原期限と明示宛先への経路で再送/保持原本の可否を判断する。期限切れ拒否は世界を変更せず、未知の受領結果をボタンから漏らさない。
4. 原本の到達期限と返書到達を分離し、不達理由を断定しない。本人がまだ受け取っていない結果を状況欄や使者ラベルに出さない。
5. 期限前/ちょうど/後、保存復旧の同じ未来・描画座標・実画像、改ざん拒否と代表回帰を実測して同ブランチへcommit/pushする。

通常の新しい撤退伝令は発送から600秒を記録する。これは120m演習範囲での技術試作値で、製品のゲームバランスとして確定した期間ではない。旧原本に期限は遡及しない。境界の実GPU試験は、同じ実WorldSessionへ明示期限入力を送り通常3Dを描画する。ユーザーが期限を編集する画面はこの工程では追加しない。通常UIの600秒入力も既存撤退/原命令ケースで検査する。

verify_unit_order_deadline.py → 実PNG/動画点検 → --finalize → check_unit_order_deadline_binding.py。verification.jsonは現行ソース・DLL・全テスト・実画像を結び付ける。固定60fps録画は性能測定ではない。全景表示は技術試作で、最終の認識に基づく可視範囲やラベルの整理は別工程。

次の5件：1.取消命令の配送/効力/未完了移動の停止、2.帰還後の軍務再任、3.複数案件の分離、4.観測/敵対に基づく対象、5.全国規模の動作検証。判断不要なら継続する。
