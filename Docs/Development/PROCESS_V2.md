# 開発の進め方 V2

本線が工程を選び、進め、報告するときの規則。今有効なものだけを書く（古い版は Git の履歴にある）。AGENTS.md と食い違う場合は、この資料を優先する。

main 統合の包括委任と、事前確認が要るもの（根本方針の変更・費用・外部公開・重要データの削除・既存権限外の操作）は AGENTS.md のとおり。

## 1. 作る単位と順番
- 単位は「差し替え前の完成」（全体100%）まで一続き（2026-11-12 ユーザー決定「次で100％になるまで進めてほしい。重大なものだけ確認してほしい」）。途中で区切って報告しない。ユーザーへの報告は、差し替え前の完成に届いたときと、本当にユーザーの判断が要るとき（下の第7節・事前確認の対象）だけ。
- main への統合は、差し替え前の完成に届いたときにまとめて1回。それまでは自分の作業ブランチにコミット・push するだけ。並行するもう一方の担当との衝突を小さくするため、main の取り込みは検査なしでこまめに行う。
- 進捗の低い枠を中心に、複数の枠をまとめて進める。一つの枠の磨き込みに時間を使わない。
- 重さの改善は、遊べない（目安：1日分の進行が60秒を超える、操作が止まる）ときだけ行い、それ以上は詰めない。
- 作る順は統合案 第14節の版（第1版：0系 〜 第5版：8〜9系）の順に沿って選ぶ。
- 作業の始めに、プレイヤーが何を選び、何が起き、どこで結果を確かめるかを決める。完成条件には必ず「最低限遊べる一巡」を入れる。
- 作業の最初の方で、土台の確認（全国の人数での重さ・進める細かさで結果が変わらないこと・途中の保存からの復旧）を1回行う。
- 例外（不達・遅着・再送・上限・代表者交代など）は代表的な1〜2件だけ入れ、残りは「例外の網羅」の工程へ回して名前と対象を記録する。
- 順番の正本は統合案 第14節。順番を変えるときは依存関係と理由を記録する。すでに作った部分は第14節と突き合わせて重複を除く。人質（D3）と従属の条項（D4）は [GETENROKU_HANDOFF_D3_D4.md](../Proposals/GETENROKU_HANDOFF_D3_D4.md) を入力にする。
- 本人の知識・物理配送・時計・保存の原則は崩さない。全知・瞬間移動・自動処刑などの近道は入れない。
- 承認済みの範囲は、全体100%または本当にユーザーの判断が要るところまで止まらずに続ける。

## 2. 検証
- 確かめるのは重大な不具合だけ（2026-11-12 ユーザー決定）。作業中：ビルド、変えた機能の代表的な一巡、変更に関係する重大な不具合の検査（短い段）。検査していない範囲を安全と言わない。
- 重大な不具合：起動不能・クラッシュ・進行不能、保存破損またはロード不能、復旧で重要な結果が変わる、金・兵・物資の増殖や二重実行、本人に未知の情報や権限の漏出。見つかればすぐ直す。
- 保存・時計・NPC の判断を変えたら、代表的な途中保存からの復旧と同じ未来を確かめる。保存形式を変えたら、影響する旧形式ごとに代表保存の読み込みとバイト一致を確かめる。
- 全件：main への統合（差し替え前の完成）の前に1回だけ。その commit を別の作業用フォルダ（git worktree）に取り出して裏で流す。重大な不具合の失敗は直してから統合し、それ以外の失敗は残件として記録する。
- 短い段と全件の分け方は、検査ごとの所要時間の記録（Docs/Development/TEST_DURATIONS.md）で決める。特に重い検査は、条件を直接作るなど同じことをより短く確かめる形へ直す。旧検査は無断で消さない。
- UI・3D に触れたら、その一巡をゲーム内部の入力と自前の描画で確かめる。
- 軽微な表示崩れ・文言・調整値は残件として記録し、進行を止めない。
- 未実施の検査は「未実施」、中断した検査は「中断」と記録する。未実行を成功へ読み替えない。
- GitHub Actions など費用の可能性がある自動実行は使わない。

## 3. 画面の確認
- 許可：ゲーム（Godot）が自分の描画を画像ファイルへ書き出すこと。ゲーム内部の入力で画面の部品を押す検査。
- 禁止：OS の画面取得・画面読み取り、マウス・キーボードの OS 操作、他のアプリの操作。

## 4. 記録と進捗
- 固定基準（approval-baseline）は、％を自分で高く付けないための保険として、作った枠の範囲を決めたときに凍結する。手間をかけない。
- 統合のとき：％の更新・完成条件の記録・PR・squash 統合・統合先の記録を1回でまとめる。記録は CURRENT_STAGE.md の「完了した工程」の表に1行と、Docs/Design の各フォルダに書く。AGENTS.md には書かない。
- 進捗表の検査（Scripts/check_progress_report.py）は AGENTS.md・OPERATING_POLICY.md・CURRENT_STAGE.md などのハッシュを持つので、変えたら progress.json の source_hashes を更新する。
- 進捗表の分母は基本設計の60枠で、数と重みは変えない。統合案の新機能は、関係する枠の完成範囲と「残り」に足す（100% は新機能も入った完成版）。範囲を足すときは「範囲の追加→再評価の版→次の基準の凍結し直し」の順で行い、加点ではなく再評価として記録する。
- 統合案の決定と食い違う基本設計は [2026-10-31_GETENROKU_BD_CHANGES.md](../Decisions/2026-10-31_GETENROKU_BD_CHANGES.md) の変更記録に沿って実装してよい。統合案にない根本変更は事前確認。

## 5. 報告と試し遊び
- ユーザーへの報告と試し遊びの依頼は、差し替え前の完成に届いたときだけ行う。1機能ごとの確認は依頼しない。
- 報告には、遊べるようになったこと・試し方・未実施の検査・既知の不具合を書き、進捗表（Docs/Development/ProgressV1/index.html）を最初に載せる。
- 届いた試し遊びの録画は解析し、分かりにくい所を直す。

## 6. 新しい機能を足すときの照合の観点
仕組みの枠だけでなく、次の観点ごとに「この機能で何が要るか」を確かめ、進捗の範囲と項目の一覧（Docs/Proposals/CHARACTER_DATA_FIELDS_V1.md）に足す。
