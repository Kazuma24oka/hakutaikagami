# 開発の進め方 V2（2026-10-31 ユーザー決定）

本線（Codex）が工程を選び、進め、報告するときの規則。統合案（[GETENROKU_INTEGRATION_V1.md](../Proposals/GETENROKU_INTEGRATION_V1.md)）第25節の決定 P1〜P8 を、本線がそのまま使える形にまとめたもの。AGENTS.md の古い規則と食い違う場合は、この資料を優先する。

main 統合の包括委任（AGENTS.md 冒頭、2026-10-30）と、事前確認が要るもの（根本方針の変更・費用・外部公開・重要データの削除・既存権限外の操作）は変わらない。

## P1 作業の単位：遊べる一巡を先に、例外は後でまとめて
- 各工程の完成条件（3〜5件）には、必ず「最低限遊べる一巡」を1件入れる。例：全国NPCの戦なら「開戦→出陣→合戦→落城→支配が変わる」。
- 不達・遅着・再送・写しの上限・代表者交代などの例外は、その工程では代表的な1〜2件だけ入れる。残りは「例外の網羅」工程にまとめて回し、工程名と対象を記録する。
- 本人の知識・物理配送・時計・保存の原則（I01〜I10）は崩さない。例外を後回しにしても、原則に反する近道（全知・瞬間移動・自動処刑など）は入れない。

## P2 工程の順番の正本
- 凍結済みの次工程（NpcPurposeV1、approval-baseline-v48）を区切りまで終えたら、統合案 第14節の順番を工程の正本にする：0a 時間の仕組み → 0b NPCの判断の土台 → 0c 史実の事件の仕組みと年代記 → 0 画面の土台 → 1〜。
- 本線がすでに作った部分（条約・人質・能力・関係・婚姻・養子・NPCの継続行動など）は、第14節の各段と突き合わせ、重複を除く。
- 順番を変えるときは、依存関係と理由を記録する。
- 人質（D3）と従属の条項（D4）は [GETENROKU_HANDOFF_D3_D4.md](../Proposals/GETENROKU_HANDOFF_D3_D4.md) を入力にする。

## P3 画面の確認
- 許可：ゲーム（Godot）が自分の描画結果を画像ファイルへ書き出すこと。ゲーム内部の入力（Godot 内部のイベント）で画面の部品を押す検査。
- 禁止（従来どおり）：OS の画面取得・画面読み取り、マウス・キーボードの OS 操作、他のアプリへの操作。
- 大きな工程の区切り（P7）ごとに、ユーザーに試し遊びの録画を依頼する。届いた録画を解析し、分かりにくい所を一覧にして次の工程に入れる。
- 実施しなかった画面の検査は、これまでどおり「未実施」と記録する。

## P4 全テスト
- PR の作業中は関連テストだけでよい。
- 資料だけの変更（コード・テスト・ゲームの資産を含まない PR）は、全件の再実行を省いてよい。その場合は「資料のみ、テスト未再実行」と記録する。
- main へ統合する前に、必ず Core の全件をローカルで流す。失敗があれば統合しない。
- GitHub Actions など費用の可能性がある自動実行は使わない。

## P5 AGENTS.md（2026-10-31 実施済み）
- AGENTS.md を今有効なルールだけにし、過去の作業記録は削除せず Docs/Archive/AGENTS_HISTORY_TO_2026-10-31.md へ移した。OPERATING_POLICY.md・CURRENT_STAGE.md も同様（Docs/Archive/〈名前〉_HISTORY_TO_2026-10-31.md）。
- 以後、工程ごとの記録は AGENTS.md に追記しない。CURRENT_STAGE.md の「完了した工程」の表に1行足し、詳しくは各 Docs/Design フォルダの README.md に書く。
- 進捗表の検査（Scripts/check_progress_report.py）は AGENTS.md・OPERATING_POLICY.md・CURRENT_STAGE.md のハッシュを持つので、これらを変えたら progress.json の source_hashes を更新する。

## P6 作業フォルダ（未実施・事前確認が必要）
- runtime-local の証跡、ComfyUI の作業コピー（.utmp）、Godot 本体（.tools）をリポジトリの外へ移す。verification.json には移した先とハッシュを残す。
- 検証スクリプトは runtime-local と .tools のパスを直接参照しているので、移す前にパスの扱いを決める。
- 重要データの操作なので、実施前にユーザーへ対象と移動先を確認する。

## P7 進捗の報告（2026-10-31 に P12 で改定）
- ユーザーへの報告と試し遊びの依頼は、「遊べる版」がまとまったときだけ行う（P12）。一段ごとの報告や確認の依頼はしない。
- 一段ごとの記録は CURRENT_STAGE.md の「完了した工程」の表と、各 Docs/Design フォルダに残すだけでよい。

## P8 基本設計との食い違い
- 統合案の決定は、ユーザーとの相談で採用済み。食い違う基本設計（BD）は [Docs/Decisions/2026-10-31_GETENROKU_BD_CHANGES.md](../Decisions/2026-10-31_GETENROKU_BD_CHANGES.md) に変更記録がある。その記録に沿って実装してよい。
- 統合案にない新しい根本変更は、引き続き事前確認。
- 進捗表の分母（基本設計60枠）は、変更記録だけでは変えない。統合案の追加範囲の扱いは次の「進捗表の範囲」に従う。

## 進捗表の範囲（2026-10-31 ユーザー決定）
- 統合案の新機能群は、**60枠の数と重みを変えずに、関係する各枠の完成範囲と「残り」に足す**。進捗表の100%は「新機能も入った完成版」を意味する。
- 完成範囲が広がるので、関係する枠の％は一度下がる（全体は57.7%から数ポイント下がる見込み）。
- ％の付け直しは 2026-10-31 に2回で済ませた（ProgressScopeV1：29枠、57.7%→51.4%／ProgressScopeV2：1回目の漏れ19枠、→49.0%）。加点ではなく再評価として記録した。次工程は再評価後の基準で approval-baseline-v48.json に凍結し直した。
- 今後、統合案に新しい範囲を足すときも、同じく「範囲の追加→再評価の版→次工程の基準の凍結し直し」の順で行う。

## 軽い進め方（2026-10-31 ユーザー決定）
ユーザーの希望：「とりあえず完成させて遊んでみる」やり方が理想。1機能ごとの確認は苦手。今までは小さな工程ごとに基準の凍結・重い検証・PR・統合・記録を繰り返し、30分で全体1%ほどしか進まなかった。次の P9〜P12 で軽くする。P1〜P8 と食い違う場合は P9〜P12 を優先する。

### P9 工程の大きさ：統合案の一段ごとにまとめる
- 第14節の一段（例：0a 時間の仕組み、中に T1〜T6 すべて）を1つの工程にする。
- 作業中は小さくコミットしてよいが、完成条件・重い検証・進捗の更新・main 統合は、一段に1回だけ。
- 凍結済みの NpcPurposeV1（基準 v48）は、すでに凍結してあるのでそのまま1工程として行ってよい。0b（NPCの判断の土台）に含めてまとめてもよい（その場合は理由を記録）。

### P10 検証の重さ：main 統合の前だけ、必要なものに絞る
- 作業中：関連テストとビルドだけ。
- main 統合の前に1回：Core の全件テスト・途中保存からの復旧と同じ未来・旧保存の互換（バイト一致）。壊れを防ぐ核なので省かない。
- 必要なときだけ：画面なしの Godot の配置照合（3D の位置・表示に関わる変更のとき）、ソース・ビルド・証跡の細かいハッシュの紐付け（保存形式や検査器を変えるとき）。
- 未実施の検査は、これまでどおり「未実施」と記録する。

### P11 記録の手順：一段の始めと終わりに1回ずつ
- 一段の始め：完成条件と固定基準を1回だけ凍結する（％を自分で高く付けないための保険なので残す）。
- 作業中：普通のコミット。小さな統合ごとの「PR との紐付け」「同じ内容の祖先の記録」のコミットはやめる。
- 一段の終わり：％の更新・完成条件の記録・PR・squash 統合・統合先の記録を1回でまとめる（統合先の記録は、統合後の作業ブランチへの main の取り込みと同じコミットでよい）。

### P12 試し遊び：遊べる版がまとまったときだけ
- 一段ごとの確認は依頼しない。いくつかの段をまとめた「遊べる版」ができたときだけ、ユーザーに通しで遊べる形で知らせ、試し遊びの録画をお願いする（P3）。
- 遊べる版の区切り（第14節の番号でまとめる）：
  - 第1版：0系（0a 時間・0b NPC の判断・0c 史実の事件・0 画面の土台）
  - 第2版：1〜3系（関係・贈り物・寺社・名声・名物・勲功・計略の情報系・席次と登用・家中職と評定・仕事・開発・奉行・技術・検地）
  - 第3版：4〜5系（能力・賊・兵種と合戦・治安・城の普請・攻城と開城・破壊系の計略・暗殺）
  - 第4版：6〜7系（血縁と死亡・婚姻と後継・家督争い・調略・家の規模・改革・募兵と陣触れ・一揆・勧告・国人衆）
  - 第5版：8〜9系（一族の分隊・官位と幕府職・取次と仲裁・天下人の到達点）
- 知らせる内容：遊べるようになったこと・試し方（どの開始で何をすれば見られるか）・未実施の検査・既知の不具合。
- 届いた録画は解析し、分かりにくい所を一覧にして次の版の工程に入れる。
