# 期限・取消命令の配送と効力・遅着競合・保存復旧（2026-10-18）

**試作規則と実測結果。正式な期限制度・取消効力・配送規格を確定しない。** ユーザーの継続依頼に基づき、`prototype/godot-foundation` の `952f892264fe3cea0d8e8a552480597f2151b68a` から実装した。main、design/foundation、既存Confirmedと既存設計資料は変更せず、既存ファイルの削除・移動も行わない。

## 今回の試作規則

[P0追加原則](../Confirmed/P0_ADDITIONAL_PRINCIPLES.md)の因果・効力時点・権限・数量整合と、[同時刻イベント統合案](P0_SIMULTANEOUS_EVENTS_CONSOLIDATED.md)の未確定境界を参照した。期限ちょうどを原則有効とするB優先案に合わせたが、正式確定には昇格しない。

| 項目 | 試作での扱い |
|---|---|
| 履行期限 | ExecuteByは絶対的な世界時刻。**その刻の徴収確定まで有効**。到達期限や返答期限とは別 |
| 期限超過 | 未確定命令だけを期限の次の刻でExpiredへ移し、未使用引当を解除。結果報告を配送する |
| 取消の発送 | それだけでは元命令を停止しない |
| 取消の受領 | 取消の受取人・受領時刻を記録する。将来の指定効力時刻までは元命令を継続する |
| 実際の取消効力 | 指定効力時刻と実受領時刻の遅い方。紛失して遅着した取消の効力を過去へ遡らせない |
| 同刻の取消と未確定徴収 | 当該刻の取消効力を先に評価し、有効ならその刻の判断・引当・徴収を止める |
| 既に徴収済み | 取消はTooLate。確定した米を返還・再徴収しない。補償処理は別工程 |
| 同刻の期限超過と取消 | 期限が既に過ぎていれば先にExpiredとし、取消の評価はAlreadyStopped |
| 同刻に複数の有効な取消 | 各取消をAppliedとして受け付けるが、実停止・引当解除・結果報告は一度だけ。登録順を反転しても同じ結果 |

共通時刻を1刻進めた後、期限超過→到達/効力を満たす取消→通常の到達/判断/徴収→失敗報告配送を評価する。これは今回の徴税ケースに限る明示的な規則で、全制度に通用する無条件の優先順位ではない。

### 認識と実行を分ける

取消や期限超過によって未確定の判断・徴収イベントを除去するが、発送済み原本・再送の物理配送は保持する。それらが後から届けば内容を本人の認識へ一度だけ登録し、実行を再開しない。通常書状を実際に受領した事実と、その命令が今も実行可能であることを混同しない。

### 権限と一意性

取消は元の発行者から同じ担当者へ送る試作条件。`cancel-tax`という明示的委任を新規セッションに設定し、発送時と効力評価時に再評価する。肩書や元命令の発行権限だけから取消権限を推測しない。受領後、効力前に取消権限が失効した場合はUnauthorizedとなり、元命令を継続する。

取消IDの再送的な再呼出しは同じ内容なら無変更、内容が異なれば拒否する。取消配送を紛失させ、後から一度だけ遅着予約できる。取消の失敗報告や正式な再送・代理受領までを完成したとは扱わない。

## 実装と画面

- `Core/Simulation/TaxSimulation.Cancellation.cs`：取消の配送・受領・効力待ち・適用・遅着・既確定/無権限評価、期限超過、保存検査。既存クラスのpartialとして責務を分割。
- `TaxOrder`：ExecuteBy、StoppedAt、CollectedAtを追加。期限内に確定した時刻と、未確定のまま停止した時刻を区別。
- `TaxSnapshot`：Cancellationsを保存しv4へ更新。配送・効力待ち・期限タイマーを未処理数に含める。
- `Game/Scripts/TaxPanel.cs`：期限なし/発送2刻後/3刻後、取消の到達時/発送3刻後/4刻後効力を選択可能。「取消命令を発送」「取消配送を紛失（試験）」「取消を1刻後に遅着（試験）」を接続。
- 取消の受領・指定効力・評価時刻、履行期限・停止・徴収時刻を表示する。内部状態を見られる検証用管理画面であり、正式な秘匿UIではない。
- 従来の即時`Cancel`は過去の管理試験用フックとして保持する。今回のUIや新規取消試験では、配送するDispatchCancellationを使用する。

## 保存v4と旧版移行

取消の全配送/効力状態、期限、停止時刻、徴収確定時刻と適用済みマーカーを保存する。受領前の有効化、未来時刻の解決、期限を越えた確定、破損した状態対応を拒否する。停止・取消・物理配送・資源更新は同じコピー→検査→公開の整合単位で確定する。

v1〜v3をv4へメモリ内移行する。変更前の実v3コードから固定セーブ8件（通常5境界、失敗報告配送中、遅着/再送中、旧管理取消）を生成し、以前のv1/v2計13件と合わせて移行を確認した。

旧保存に存在しなかった期限・取消命令・取消権限は付与しない。過去に確定済みで正確な徴収時刻が保存されていないものは、CollectedAt不明のまま維持し、時刻を推定して捏造しない。新しい徴収には確定時刻を記録する。

通常保存は `user://tax-prototype-v4.json`。それがないときだけv3、v2、v1の順に既存保存を探す。保存はv4へ行い、旧ファイルを消去・上書きしない。試験は `user://deadline-smoke-<GUID>.json` を使う。

### 実際に通した6条件

1. 期限2：時刻2で引当60を保存。時刻3で期限超過し、引当0・蔵100。保存から再開しても同じ。
2. 期限3：時刻3ちょうどに徴収60が確定し、蔵160・CollectedAt=3。
3. 取消は時刻1受領/時刻3効力：時刻2まで引当60を保持。時刻3の徴収直前に取消し、保存から再開しても蔵100・引当0。
4. 取消紛失/早い遅着：時刻1に紛失、時刻2に遅着して取消。有効時刻を1へ遡らせず、実評価は2。
5. 取消紛失/遅い遅着：元の徴収が時刻3に確定後、時刻4の取消遅着はTooLate。蔵160を維持。
6. 原本/再送と取消の競合：原命令の紛失報告が届いた後、原本を時刻6に遅着予約し再送。取消が再送分と同じ時刻3に届いて効力を持つ。保存地点へ戻しても、原本・再送分の2通は物理到達し、命令内容の認識1件・判断/徴収0・蔵100・未処理0を維持。
