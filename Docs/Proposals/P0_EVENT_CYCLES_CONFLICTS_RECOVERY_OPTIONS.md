# P0イベント処理：循環依存・競合・失敗復旧のABC比較

**状態：未確定（Proposals）／2026-10-17。** 6項目ともABC未選択。Bは推奨候補。既存の確定原則を維持し、実際の解消・復旧手順を比較する。

## ① 循環依存の検出と解消
- **A**：循環を検出せず相互に待機。例：開城が援軍を待ち、援軍も開城を待って停止。
- **B（推奨）**：依存循環を検出し、根拠がない自動成立を防ぎ、保留・裁定・安全な失敗へ移す。例：開城と援軍が互いを条件とするなら双方を自動成功させず審査する。
- **C**：循環中の全イベントを同時成功。例：同じ城が開城済みかつ未開城になる。
- **保留**：循環の検出単位、保留期限、代替行動、ユーザー通知。

## ② 独立した同時刻イベントの優先順位
- **A**：登録順のみで確定。例：徴税請求が先に登録された勢力が全て取得。
- **B（推奨）**：因果・効力時点の評価後、権限・引当・戦況等の制度別裁定へ渡す。例：米100俵に各80俵の請求があれば残量を守りつつ優先権を審査。
- **C**：毎回ランダムに勝者を決める。例：開城と援軍の結果がロードごとに変わる。
- **保留**：裁定規則の優先階層、同時刻境界、タイブレーク。

## ③ 更新途中の失敗とロールバック
- **A**：部分的な更新を残して続行。例：兵糧出庫だけ成立し輸送記録が消える。
- **B（推奨）**：整合単位内の未確定変更は取り消し、確定済み変更は別の補償処理で扱う。例：出庫前に失敗した輸送は取り消し、出庫確定後の事故は返還取引を記録。
- **C**：失敗時に全世界を常に直前まで巻き戻す。例：遠方で既に成立した条約まで取り消す。
- **保留**：確定境界、補償の可否、外部通知の取消、世界停止。

## ④ 補償処理の重複と失敗
- **A**：補償は記録せず都度実行。例：米返還を再試行するたび二重返還する。
- **B（推奨）**：補償を追跡可能な独立処理として管理し、重複適用を防ぎ、失敗は保留・再試行・要対応へ移す。例：輸送失敗による米返還を二重適用せず、返還失敗なら未完了として残す。
- **C**：補償が失敗しても成功扱い。例：戻っていない米を返還済みにする。
- **保留**：補償ID、再試行回数、不可逆イベント、責任の扱い。

## ⑤ 再試行・再開の条件
- **A**：失敗時に無制限即時再試行。例：不正な城主権限での命令を永久に再実行。
- **B（推奨）**：一時的失敗と恒久的失敗を区別し、前提条件を再評価して安全に再試行／中止／保留する。例：通信遅延は再送し、権限取消済みの命令は再検証する。
- **C**：失敗イベントを全て破棄。例：一時的な処理失敗で徴税が消滅する。
- **保留**：再試行上限、バックオフ、期限切れ、エラー分類。

## ⑥ セーブ・ロード中の未完了処理
- **A**：未完了の途中状態をそのまま確定。例：保存中の徴税が適用済みと未処理の両方になる。
- **B（推奨）**：確定記録と未完了処理を整合する形で保存し、再開時に安全に復旧・再判定する。例：落城の状態更新途中で保存しても二重落城せず再開する。
- **C**：未完了イベントを全て新規イベントとして再生成。例：ロード後に徴税が二重発生する。
- **保留**：チェックポイント粒度、保存の原子性、乱数状態、互換性。
