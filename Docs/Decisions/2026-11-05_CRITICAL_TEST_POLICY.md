# 検査を重大不具合優先に変更

## P13 重大な不具合を優先する検証（2026-11-05 ユーザー決定）

ユーザー指示：「運用ルールを見直して。クリティカルなエラーが出なければそれでいい」。P4・P10および旧資料の全件実行必須より、この規則を優先する。現在の0bにも適用する。

- 通常の統合条件は、ビルド成功、変更した機能の代表的な一巡、変更に関連する重大な不具合の検査に合格し、既知の重大な不具合がないこと。全件合格は要求しない。検査していない範囲まで安全と断定しない。
- 重大な不具合：起動不能・クラッシュ・進行不能、保存破損またはロード不能、復旧で重要な結果が変わる、金・兵・物資の増殖や二重実行、本人に未知の情報や権限の漏出。これらは見つかれば統合前に修正する。
- 選ぶ検査は変更箇所と依存関係から決め、対象の名前と理由を実行前に記録する。新規検査を無条件にすべて実行しない。関係する主要分岐と失敗の代表を確認する。
- 保存・時計・NPC判断などを変更した場合は、代表的な途中保存からの復旧と同じ未来を確認する。保存形式を変更した場合は、影響する旧形式ごとに代表保存の読込・必要なバイト一致を確認する。過去の全証跡を毎回再実行しない。
- UI・3Dに触れた場合は当該一巡の内部入力・自前描画を確認する。OSの画面取得やGUI操作は禁止のまま。
- 長期シミュレーション、全件実行、例外の網羅、大規模性能測定は通常の統合の停止条件にしない。遊べる版の区切りで必要性を再評価して実施する。既知の重大な不具合の再現に必要なら、関係する検査だけを追加する。
- 軽微な表示崩れ・文言・調整値などは残件として記録し、進行を止めない。完了した検査を理由なく繰り返さない。
- 時間のかかる検査は、まず条件を直接作って短くできるか検討する。資金枯渇の検査に仕事51回、調達優先順位の検査に数年の経過を毎回要求しない。旧検査は無断削除せず保持する。
- 既存の検査器が全件数を固定要求する場合は、今回の検査計画と結果を検証する形に改める。未実行を成功へ読み替えない。中断した全件実行は中断と記録する。
- main統合・コミット・pushの包括委任、素材の保護、費用と根本変更の承認条件は維持する。

0bの凍結済み条件に含まれた「全件」は本ユーザー決定により必須から外す。元の固定基準は改変せず、検査結果には実行範囲と未実施を記録する。進捗の分母と目標値は変更しない。
